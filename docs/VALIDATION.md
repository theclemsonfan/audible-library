# Validation evidence — Next Chapter 0.2.0

Prepared October 29, 2026.

## Executed successfully

**101 automated Node tests** passed, with no failures, cancellations or skipped tests. These exercise the real application/model/store/HTTP code and actual background-worker source with a simulated Chrome API. The worker simulation communicates with a real local instance of the new HTTP backend. Synthetic extractor results were generated by the separate rendered-DOM checks.

Covered: account setup/login, password hashing, session digests and logout, origin checks, hidden-file guards, one-time pairing, expiration and token revocation, scope-limited tokens, staged imports, idempotent acknowledgement/finalization, out-of-order/duplicate pages, incomplete-scan preservation, count-drop guard, transaction merging, historical purchase/refund precedence, local-only reading overrides, server persistence/reopen, consistent backups, reconstruction of worker state after suspension, pause/resume, tab disappearance, run-creation network retry, stop, weekly due/catch-up logic, and alarm recreation.

**23 rendered Chromium DOM/UI checks** passed. These used `set_content` with owned synthetic documents; they did not navigate to Audible or load a private account. They cover the final-segment ASIN, wishlist exclusion, visible versus hidden Finished markers, progress/time, authors/narrators/series, actual forward-button wording, final-page detection, discovered filter values, refund/listening dates, catalog context, changed-layout/verification stop conditions, honest empty state/sample mode, mobile search/details/series/settings, and uncaught JavaScript errors.

**Static release checks** passed: 19 JavaScript files parsed, JSON files and entry points validated, and an extension permission guard passed. Compose and CI YAML parsed successfully.

**Five real local HTTP deployment probes** passed: health and public setup status return 200; unauthenticated library access returns 401; database and setup-key paths return 404. This exercises the actual server, not a mocked endpoint.

**Visual inspection** completed for the rendered desktop and 390-pixel phone sample UI. The phone layout passed a horizontal-overflow check. Screenshots contain explicitly fictional sample titles, not imported user books.

Build environment: Node.js 22.16.0, SQLite 3.49.1 via node:sqlite, Python 3.13.5, Playwright 1.57.0, installed Chromium. Docker configuration targets Node 24. Runtime application has no external npm dependencies.

## Not executed / not established

- No installation of the actual extension in the user's Chrome or Brave profile.
- No new live Audible account scan, no real import count, no validated archival completeness.
- No seven-day real-time scheduled run. Schedule logic, saved-state recovery and catch-up were tested, not a week of live behavior.
- No real extension permission-dialog or Chrome-origin network handshake test. The HTTP endpoints and simulated worker requests were tested; the actual browser-host permission handshake remains an installation acceptance test.
- No native iPhone/Safari test. Responsive Chromium rendering is not the same as actual iOS testing.
- No Docker build/run or public HTTPS deployment in this environment, because Docker is unavailable here.
- No independent penetration test or security certification.

The environment's managed Chromium rejected network navigation, including a localhost fixture navigation, with ERR_BLOCKED_BY_ADMINISTRATOR. No browser policy, network restriction or Audible protection was bypassed. Rendering and DOM checks used in-memory synthetic documents instead. This is a limitation of that test environment, not evidence that Audible blocks the user's browser.

## Release acceptance at home

Install the bundle and extension, complete app setup and one-time pairing, sign in to Audible normally, run a full sync, inspect the last-success count/coverage report, and compare sample series and statuses. Then close/reopen the desktop browser to check actual checkpoint/schedule behavior and open the HTTPS-hosted app from the phone. If a site's real markup differs from the supported adapter, the software must pause or report a coverage warning rather than claiming success.

A staged backend and a tested adapter are not the same as a production-verified integration. This build is ready for installation/deployment validation; live account/host acceptance is the remaining boundary.
